# FF3 ダメージ式（instructrtrepe FAQ）との比較メモ

このメモは、`combat` 実装を FAQ 記述と突き合わせた差分整理です。

## 一致している点（主なもの）

- 物理の基礎式（攻撃力・防御差・1.0〜1.5乱数）を採用している。
- 物理の命中計算は `A.M*Hit% - D.M*Evade%` の期待値近似。
- Mini/Toad 時の「攻撃側0ダメージ」「被攻撃側防御0」扱いが入っている。
- 後列時の物理命中半減、Blind 時の命中半減を実装している。
- 魔法の黒/白/召喚で威力・倍率・命中率を分ける方針は FAQ と整合。

## 齟齬がある点（要注意）

1. **物理ダメージの下限**
   - FAQ: 「M>0 なら最終ダメージ最小 1」。
   - 実装: 1ヒット単位で `max(base,1)` を適用しており、結果的に FAQ よりダメージが高く出やすい。

combat/phys_damage.py で、物理ダメージの最低保証を「1ヒットごと」ではなく「最終ダメージ段」で適用するよう変更しました。これにより、低い基礎ダメージで多段ヒットしたときに FAQ より高く出やすかった挙動を抑え、NES版FF3に近い方向へ寄せています。
同じ下限処理を、character -> enemy と enemy -> character の両方の物理ダメージ計算経路に適用しました。キャラ側は総ダメージ算出後に floor を通す形へ変更し、敵側も同様に統一しています。
回帰防止のため、低攻撃力・高防御・複数ヒット時に「旧実装なら 2 以上になりやすいが、新実装では最終 1 になる」ケースを、攻撃側/被攻撃側の両方向でテスト追加しました。

2. **Hit% 上限**
   - FAQ: 物理 Hit% は 99 上限（その後に半減ペナルティ）。
   - 実装: `_calc_net_hits` で 100 まで許容。

combat/phys_damage.py に _cap_physical_hit_percent() を追加し、物理 Hit% を FAQ に合わせて 99 上限へ統一しました。また _calc_net_hits() でもこの上限を使うようにして、期待値計算側でも 100% を超えないようにしました。
physical_damage_char_to_enemy() では、武器の命中率を取得した直後に 99 上限を適用し、その後で Blind と後列ペナルティを半減としてかける順序へ修正しました。これにより「99 上限 → 半減ペナルティ」という FAQ の流れに近づいています。
physical_damage_enemy_to_char() でも同様に、敵の accuracy_percent をまず 99 に丸め、その後で Blind / 後列ペナルティを適用するように揃えました。
tests/test_phys_damage_floor.py に、攻撃側・敵側の双方で「120 Hit% がそのまま使われるのではなく、99 に丸められてから半減される」ことを確認する回帰テストを追加しました。既存の物理ダメージ下限テストも引き続き維持しています。

3. **物理 M（ヒット数）算出方法**
   - FAQ: 1ヒットずつ確率判定するループ。
   - 実装: 期待値 `A.M*h - D.M*e` を直接使う近似（表示ヒット数は丸め）。

combat/phys_damage.py の _calc_net_hits() を拡張し、use_expectation=False の乱数モードでは FAQ に寄せて「攻撃側のヒット判定を 1 回ずつ」「防御側の回避判定も 1 回ずつ」行い、その差分から実効ヒット数を決めるよう変更しました。期待値モードは既存互換のため維持しています。
physical_damage_char_to_enemy() / physical_damage_enemy_to_char() から _calc_net_hits() に rng と use_expectation を渡すようにし、乱数モードでは整数ヒット数をそのまま使い、期待値モードでは従来どおり近似値を丸める整理にしました。
tests/test_phys_damage_floor.py に、スクリプト化した RNG を使って「4 回の攻撃判定・2 回の回避判定から最終 2 ヒットになる」ケースを、キャラ側・敵側の両方で検証する回帰テストを追加しました。既存のダメージ下限テストと Hit% 99 上限テストも引き続き残しています。

4. **クリティカル仕様**
   - FAQ: 未確定事項として扱い。
   - 実装: 独自確率（Agi依存）で 2 倍を採用。

観測値: 経験的な観測では「2倍」のように見えることが多いとされています。
解析上の疑問: しかし、最終ダメージが必ずしも2の倍数にならないことから、計算の最終ステップで単純に2倍しているのではなく、計算の初期段階（基本攻撃力の算出など）で何らかのボーナスが適用されている可能性が高いと推測されています。
未確定事項: そのため、NES版の厳密な計算式において「どこで、どの程度の倍率が掛かるのか」は、専門的な解析者たちの間でも「未確定事項」として扱われています。
**DS版（リメイク版）においては、クリティカルヒットは明確に「ダメージが2倍にはね上がる」**仕様として公式ガイドに記載されています。
NES実機の挙動を100%正確にシミュレートしたい場合は、単なる最終ダメージの倍増ではなく、基本ダメージの算出ステップ（Step 1）付近でボーナスを適用するなど、より複雑なアルゴリズムの検討が必要になるが、どうすればよいか方法は定かでないので、適用を見送り

5. **魔法の最低ダメージ**
   - FAQ: `M>0` なら最終 1 ダメ保証。
   - 実装: 1ヒット単位で `max(base,1)` を適用。

combat/magic_damage.py で、魔法の 1 ヒット基礎ダメージから max(base, 1) を外し、FAQ に寄せた _apply_magic_damage_floor(...) を追加しました。これにより、ヒットが成立したときだけ最終合計ダメージに最低 1 を保証する形へ変更しています。
同ファイルの magic_damage_char_to_enemy() と magic_damage_enemy_to_char() で、各経路の合計ダメージ算出後にのみ下限 1 を適用するよう修正しました。これで「1ヒットごとの底上げ」ではなく「最終段での最低保証」になっています。
あわせて calc_drain_damage_generic() でも同じ最終段 floor を使うよう統一し、攻撃魔法系の内部式が揃うようにしました。
回帰テストとして tests/test_magic_damage_floor.py を追加し、キャラ→敵・敵→キャラの両方で「旧実装ならヒット単位で底上げされるケースが、新実装では最終 1 になる」こと、およびヒット数 0 のときは floor しないことを確認しています。

6. **全体化ペナルティの対象**
   - FAQ: 自動全体対象（例: Quake / Meteo / Call）には分割ペナルティなし。
   - 実装: `SpellInfo.auto_all_target` を導入し、`Target` が `All Enemies` / `All Allies` の魔法は `split_to_targets > 1` でも分割しない。

combat/magic_damage.py の魔法最低保証をさらに整理し、最終ダメージ段でのみ 1 を保証するように修正しました。具体的には、1ヒット基礎ダメージはそのまま返し、_apply_magic_damage_floor(...) を使って「ヒット成立後の最終値」にだけ下限をかける構成です。
magic_damage_char_to_enemy() は、合計ダメージ計算のあとに属性補正と split_to_targets を反映し、その最後に floor を適用するよう変更しました。これで「全体化で 0 に落ちたが、FAQ 的には最終 1 を保証したい」というケースも扱えます。
magic_damage_enemy_to_char() も同じ順序に揃え、敵→キャラ側でも floor の適用位置を統一しました。また calc_drain_damage_generic() でも同じ helper を使うようにして、攻撃魔法系の内部式を揃えています。
tests/test_magic_damage_floor.py に回帰テストを追加・拡張し、キャラ→敵、敵→キャラ、split 後でも最終 1 になること、およびヒット数 0 のときは floor しないことを確認できるようにしました。

7. **FAQ 固有の特殊仕様の網羅度**
   - 個別修正しやすいように、齟齬候補を以下に分解する。
   - **Haste**: FAQ では Step1-6 相当で求めた `Final Damage` を物理 Base Damage 加算、`M` を Attack Multiplier 加算に使う。現状は回復/補助判定と回復量計算はあるが、FAQ 通りの「別計算結果を物理へ転写する専用処理」としては整理されていない。

   Haste を「その場で main_power / main_atk_multiplier を直接書き換える処理」から、FAQ 準拠で魔法式から Final Damage と M を計算し、それを物理用の加算ボーナスとして保持する形へ整理しました。あわせて、キャラ・敵の最終ステータスに Haste 専用の一時ボーナス領域を追加しました。.
   物理ダメージ計算側で、その Haste ボーナスを物理 Base Damage 加算と Attack Multiplier 加算として反映するよう変更し、キャラ側・敵側の通常攻撃の両方で使うようにしました。.
   キャラの Haste 詠唱、敵の自己 Haste、Bacchus's Cider の Haste 相当処理を新しい転写ロジックに載せ替え、ログも「物理加算値 / 攻撃回数加算」を表示する形に更新しました。.
   Haste が基礎ステータスを破壊せず、転写ボーナスとして蓄積されて物理計算時に効くことを確認する回帰テストを追加しました。

   - **Safe (Protect)**: FAQ では Step1-6 相当の `Final Damage` を Defense / Magic Defense へ加算する。現状は Safe 系の補助概念はあるものの、FAQ の加算先・加算量を一貫して再現する専用処理が不足している可能性がある。

   Protect/Safe 用に calc_protect_buff_amount() を追加し、従来の単純な base_power * base_factor * (1.0〜1.5) ではなく、FAQ の Step1-6 相当の魔法式から得た Final Damage を Defense / Magic Defense の加算量として使うようにしました。これにより Safe (Protect) の加算先と加算量が Haste と同じ転写ロジック基盤で一貫するようになりました。
   キャラの Protect、敵の Protect、そして Turtle Shell の Protect 相当効果を、新しい Protect 転写ヘルパに接続しました。各処理で対象側の magic_defense / magic_def_multiplier / 魔法耐性を渡すようにし、ログにも今回の加算値を明示するよう更新しました。
   味方対象の Haste / Protect / Safe 系転写で、FAQ の self-targetting どおり Magic Defense と Magic Defense Multiplier を 0 扱いにする buff_target_magic_parameters() を追加しました。これで、味方に Protect を掛けたときに対象自身の高い魔法防御のせいで +1 まで潰れる問題を防げます。
   
   - **Kill のレベル閾値**: FAQ では `IF Target Level >= ((((Attacker Level)/2)*3)/2) THEN Hit%=0`。現状は通常の魔法命中式中心で、Kill 専用のレベル門番を明示した処理差し込みが必要。
   - **Wall (Reflect) 反射**: FAQ では「次に受ける反射可能魔法を敵側へ跳ね返し、1回で消える」。現状は reflect 用の状態値は存在しても、FAQ 基準の対象判定・反射先・消費タイミングまで含む厳密再現かを個別確認する必要がある。
   - **Terrain Backfire**: FAQ では Geomancer の Terrain が全対象で `M<=0` のとき `Ineffective` ではなく `Backfired` になり、使用者が `MaxHP/4` ダメージを受ける。現状は Terrain を黒魔法寄りに扱う前提はあるが、この専用失敗処理を独立に点検・実装する余地がある。
   - **Cure4 (Curaja) 単体全回復**: FAQ では単体対象時のみ全回復、複数対象時は通常計算。現状も近い実装はあるが、FAQ の単体/全体分岐と完全一致かは回復ルート全体で再確認したい。
   - **WWind (Tornado)**: FAQ では `Final Damage` を使わず、成功時に HP を `(Spell Damage..Spell Damage*2)` に直接する特殊処理。通常ダメージ式とは別分岐が必要。
   - **自分側対象時の防御0処理**: FAQ では味方への物理は Defense=0、味方への魔法は Magic Defense / Magic Defense Multiplier = 0。現状も一部同趣旨の処理はあるが、攻撃種別ごとに漏れなく統一されているか要確認。

## まとめ

- 「黒/白/召喚の基本骨格」は概ね一致。
- ただし **“FC/NES 厳密再現” という観点では、期待値近似・下限処理・Hit上限・特殊効果網羅で差分あり**。
- バランス調整目的なら現実装でも運用可能だが、FAQ完全準拠を目指すなら上記 1〜7 の調整が必要。

## Summary
ご提示の FAQ と現行実装を照合した結果、完全一致ではなく、いくつか明確な齟齬があります。特に、ヒット数を逐次乱数ではなく期待値近似で扱う点、物理/魔法の最低ダメージの扱い、Hit%上限、クリティカル仕様は差が大きいです。analysis/damage_formula_faq_comparison.md に比較結果を整理しました。

物理側では、_calc_net_hits が A.M*h - D.M*e の期待値近似（かつ Hit% を 100 まで許容）になっており、FAQ の「1ヒットずつ判定」「物理Hit%上限99」と差があります。また 1ヒット基礎ダメージに max(base,1) をかけるため、FAQの「最終段で最低1保証」と厳密には挙動が異なります。

クリティカルは FAQ 側では未確定扱いですが、実装では Agi 依存の独自確率＋2倍が入っています。

魔法側も黒/白/召喚の威力・倍率・命中の骨格は概ね FAQ 準拠ですが、ヒット数は期待値近似、1ヒット基礎ダメージで max(base,1)、全体化時の分割は split_to_targets>1 で一律適用という設計で、FAQの「自動全体対象は分割なし」等と差分が出ます。

なお、ステータス算出の基礎式（攻撃力/防御/防御倍率/魔防倍率など）は FAQ の定義に沿った項目が多いです（Agi, Level, JobLv を使う構成）。
